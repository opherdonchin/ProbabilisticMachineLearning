**What this establishes:** every proposed hands-on lecture now points to an *inspectable implementation or fully written worked solution* of an explicitly named dataset/model/problem. **What it does not establish:** the external code has not been run, adapted to the course's modern notebook environment, timing-tested, or validated in Colab.

A good course notebook starts by reproducing a verified worked answer and only then converts the solution to an instructor narrative and student exercise. Avoid choosing a general subject and writing an unrelated “wish list” of operations.

## Interpretation / next step

These links establish **reference provenance**, not final student exercise contracts. The next per-lecture validation should be to: (1) run the source or an equivalent faithful implementation from a clean kernel; (2) identify the exact model/data/outputs that will be retained; (3) estimate what can be done by students in one hour; and (4) build the worked solution before writing the student-facing notebook.

For L3 specifically, choose whether the sprinkler example is a good substantive *graphical-model* notebook; its actual implementation provides a more honest starting point than designing an entirely fictional medical example. This can be decided during L3 scoping.
