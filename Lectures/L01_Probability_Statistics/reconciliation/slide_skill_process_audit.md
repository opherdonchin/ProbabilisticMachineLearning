# L01 slides 64–65: process audit at 4b69e7e

Read-only audit by `/root/slide_process_audit`. Repository artifacts, stage skills/conventions/API, source neighbors and three actual handout renders were inspected. The coordinator supplied the exact historical prompt excerpts quoted below from its own transcript; those excerpts were not independently recovered from a stored transcript by this auditor. No repository files changed. This report distinguishes artifact evidence, prompt evidence and causal inference.

## Finding

This was a chain of incomplete contracts and incomplete checks, not evidence that an author simply ignored a fully specified style requirement. The designer already put substantial framing/interpretation inside the mathematical object and mislabeled newly derived expectations as recall. Authoring then introduced an additional semantic error by lowering typed key points into the object grid. The feasibility preview mainly asked whether this design could be implemented, and the final checks treated readable, complete, unclipped renders as sufficient. None of those gates explicitly tested the instructor's recognizable division of labor: objects are usually light on text; necessary explanation belongs in key points.

The instructor's new statement is more precise than the existing written convention. It should become an authoritative design rule, with carefully bounded exceptions for intrinsic diagram labels and logically necessary proof conditions. A prose prohibition or mechanical word budget would be a poor substitute: existing good proof slides have short statements where mathematics depends on them.

## Evidence and causal chain

1. **The coordinator's build envelope prioritized coverage.** Its historical design prompt specified TWO slides, local notation `m=E[z|y]`, `V=Cov[z|y]`, a residual `r`, every identity and Gaussian specialization; it said “Prefer 2–3 cumulative reveal states per slide, readable normal sizes, exact visible mathematics and assumptions.” The persistent organization also fixes two slides and an unmeasured 2–4 minutes (`reconciliation/squared_loss_slide_organization.md`, extent paragraph). This did not supply a concrete object/key-point style contract. It could encourage compressing a complete mini-exposition into two screens, but there is no evidence that two slides are inherently inadequate or that count caused the errors.

2. **Several faults originate in Slide Design, before production.** `reconciliation/squared_loss_slide_design.typ:74–83` makes the object contain two long instructional headings and a reconstruction sentence. At `:135–142`, the three expectation calculations are placed in `recall-card`; at `:191–193` they are explicitly called “subordinate carried-forward algebra.” The previous slide establishes the residual expansion, not those expectation calculations. This is a false pedagogical classification, not a font/spacing problem for the author to solve. At `:144–153`, lengthy interpretive underbrace labels and several titled mathematical cards create multiple competing textual frames. The design was mathematically substantive, but its chosen visual explanation was inconsistent with the surrounding deck's usual economical objects.

3. **The written design standard was weaker than the instructor's norm.** `Lectures/slide_design_conventions.md:108–125` says prefer the mathematical/visual object over describing it in prose, and `:136–146` calls for short retained key points. These instructions support the instructor's preference but do not explicitly assign framing/interpretation to a separate region or require justification for prose retained in objects. The skill requires neighboring slides (`.agents/skills/slide-design/SKILL.md:30–40`) and visual hierarchy review, but the saved output gives no concrete precedent comparison showing what was learned from those neighbors. We cannot establish from artifacts whether the designer read, forgot or interpreted the neighbors differently.

4. **The design representation preserves labels but weakens role boundaries.** `Lectures/design.typ:107–112` types key points; `:669–691` subsequently concatenates `cards + key-points` into one `objects` collection. `layout-grid` places all labels as peers, and `_validate` (`:383–419`) validates labels/references/placement without checking object-versus-interpretation roles. In the failed design, both ordinary cards and typed key points are cells in the same grid (`squared_loss_slide_design.typ:122–130`). The A4 design render shows layout as boxes of labels (`design.typ:438–486`), separately from object bodies (`:713–718`); it does not itself test the slide's final visual text density. That is an affordance contributing to the failure, not proof that the API forces bad slides.

5. **Authoring introduced a detectable lowering error.** On production slide 65 (`slide_deck.typ:2758–2820`), the `validity` and `interpretation` bullets are inside `object:` at `:2810–2815`, and no `key-points:` argument is supplied. They had remained typed key points in the design (`squared_loss_slide_design.typ:156–163`). This violates semantic-role preservation, already required by `.agents/skills/slide-authoring/SKILL.md` and the explicit ordinary-slide convention `Lectures/slide_authoring_conventions.md:114–139`. It is not merely a missing new style rule. The production author copied the layout sketch but lost the semantic distinction; backpressure should have reconciled any tension instead of flattening everything. The shared `content-block` API would have produced the familiar distinct ruled takeaways region if key points were passed in their proper slot (`Lectures/course.typ:602–625`).

6. **The preview did not validate quality/alignment.** The same Slide Authoring agent reviewed the designer's provisional work, then built it. Its preview was independent of the designer, but not an independent reviewer of its own eventual implementation. The saved report (`squared_loss_authoring_review.md:9–11`) identifies unconstrained action-space clarification and density risk; it checks API support. The action-space repair adds the sentence now prominent inside the object. The coordinator says the preview task emphasized API/overflow and existing attachment problems. This is useful feasibility checking, but not a comparative design review. Calling the preview independent is accurate only with that restricted meaning.

7. **The final review narrowed the skill's broad visual gate.** The authoring skill already requires hierarchy, alignment and design fidelity (`slide-authoring/SKILL.md:137–143`). The saved build report (`squared_loss_authoring_review.md:25–31`) proves attachment checking, successful compiles, inspected states and no reported clipping/literal macros; it accepts slide 65 as dense but readable. Its coordinator review conclusion is about clipping, overflow and reveal order. The coordinator confirms that its attention was on those mechanical/rendering concerns rather than semantic roles or economical objects. Thus the gate was performed too narrowly, and there is no saved evidence of a render comparison against an established proof and immediate neighbors. The review script itself correctly labels its verdict `mechanical-pass`; it did not claim to judge pedagogy (`scripts/review_slides.py:107–109`). The human/agent interpretation expanded that success into adequate production quality.

8. **The later critique was question-dependent and seeded.** The coordinator supplied this exact posthoc reviewer prompt excerpt: “Identify recall-card misuse: slide65 expected terms are newly derived math, not just previous slide recall. Identify content-block key points moved into object on65, fixed-space reveals if relevant, latent original residual-name collision.” Consequently, the later review was separate from the builder but not blind discovery of the same faults. Agreement on those seeded hypotheses is corroboration after direction, not independent detection. There is no evidence for a model-specific psychological cause. In particular, this audit does not find a substantive `r` collision: earlier `r=x1−mu1|2` (`slide_deck.typ:2007,2059,2175`) and new `r=z−m` are the same centered-residual construction in renamed variables. Extra `m,V` notation has a continuity cost, but do not invent a collision because a prompt suggested one.

## What was present, absent, or ambiguous

- **Present but not obeyed:** object/key-point semantic role preservation in authoring; raising design backpressure; the broad visual review obligation; recall as earlier material rather than new proof.
- **Insufficiently explicit:** the instructor's objects-light-on-text norm and how to distinguish essential mathematical labels/conditions from explanatory prose. General “prefer showing” language did not operationalize that norm.
- **Orchestration weakness:** downstream feasibility was treated as enough design reassurance; the same reviewer became implementer; the root checked final renders narrowly; posthoc seeded review was described without its limitation. Multiple agents did not create multiple independently tested quality criteria.
- **Representation weakness:** generic label grids weaken role boundaries and sketch only label boxes. They cannot certify density or semantic recall truth. Preserve roles structurally where possible; do not pretend a semantic lint proves slide quality.
- **Unestablished causes:** model choice/effort, not actually reading files, context loss, or two-slide impossibility. These are not demonstrated by this case.

## Minimal changes with a mechanism to test

1. **Design:** add the instructor's specific rule in course conventions and make the design skill extract a short visual/notation contract from an existing proof and an immediate neighbor before choosing object content. The contract should distinguish concise intrinsic labels/necessary proof conditions from explanation intended for key points. This supplies a generative constraint, rather than another closing checklist. Every surviving prose sentence inside an object should have a concrete instructional reason; it need not have a fixed word limit.

2. **Design/authoring handoff:** require an ordinary-slide composition to distinguish mathematical object area from key-point area even when either contains a grid. Preserve typed `key-points` at lowering; contradictory placement is design backpressure, not production freedom. A small `layout-grid` key-point slot or a wrapper around object layout is a plausible API repair, but update shared API only after a concrete repeated need. A focused structural check could catch role flattening; it cannot establish that the prose or derivation is good.

3. **Recall and reveal authority:** classify each mathematical item as already established or newly derived, with a specific prior source for recall. New expectation steps must be ordinary proof objects, and reveals should advance the mathematical argument rather than merely expose layout groups. The role classification prevents an author from correctly making the wrong thing subordinate.

4. **Review:** make one comparison-based design/production review distinct from feasibility and mechanical checks. It must view the candidate and relevant existing proof/neighbor renders and return specific visual-role evidence. A reviewer should receive the standards and mathematical contract, not the expected defects, the builder's defense or the coordinator's preferred verdict. Do not call separate-agent agreement independent detection when hypotheses were seeded.

## Suggested bounded experiment

Use slide 64 as calibration and slide 65 as an untouched transfer case. Preserve baseline `4b69e7e` in Git; do not redesign the lecture or change approved mathematics while investigating.

- Before editing skills, freeze the mathematical contracts, precedent slides and success criteria. Criterion examples: the mathematical object is quickly identifiable; explanatory/framing prose is in the distinct key-point region except justified intrinsic annotations; prior material is truly prior; new reasoning retains normal classroom size and appropriate reveal emphasis; necessary assumptions remain visible and exact.
- Have fresh, skill-loaded design and authoring agents work on slide 64 using those frozen inputs, without handing them the posthoc defect catalogue or a prescribed corrected layout. Review the resulting renders with another fresh agent. Preserve actual prompts/artifact revisions and separately report correctness, design fidelity, comparative alignment and mechanical outcomes.
- Use a fresh reviewer on the *old* failed render as a detection control, with the same standards and neighbors but no issue hints. If it accepts the old failure, the proposed review procedure is unvalidated even if the new slide looks better.
- Refine only changes shown useful by the calibration, then freeze skill/convention versions. Run slide 65 through new fresh designer and authoring agents, providing its mathematical contract and the needed previous slide, but no slide-specific criticism and no desired arrangement. This tests transfer of role/style discipline. Because slide 65 builds on slide 64, it is a transfer test, not a statistically independent trial.
- If slide 65 fails, record that as a failed holdout. Once its feedback is used for refinement it becomes another development example; do not rename the same repaired case a successful independent validation. A further unrelated slide or proof is needed for new transfer evidence.
- Improved results would support the concrete process changes on this small task; they would not prove the skills reliable course-wide or show which model caused the old failure. Fresh-agent repetition after every diagnosis can also merely learn the evaluator's preferences. Avoid “iterate until done” as a substitute for a frozen transfer test.

The right immediate repair is to establish and test a reliable visual-role contract. Rebuilding the entire deck would multiply the same inadequately measured process rather than diagnose it.
